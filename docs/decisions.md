# 决策记录（ADR，草案）

ADR（Architecture Decision Record，架构决策记录）：每条写明决定、日期、理由和被放弃的替代方案。决策变更时追加新条目并注明取代关系，不改写旧条目的含义。

| # | 决定 | 日期 | 理由 | 放弃的替代方案 |
|---|---|---|---|---|
| D1 | **Markdown 优先的混合式生成 UI**：默认是 Markdown，只有确实适合结构化展示的信息才用语义块 | 2026-10-26 | 多数回答是解释和结论，Markdown 最自然；结构化只用在指标、表格、图表、交互上，避免“为了 UI 而 UI” | 整条消息由模型生成 UI 树（延迟高、校验面大、风格难统一）；纯 Markdown（无法承载交互和可读的数据展示） |
| D2 | **语义与表现分离**：块只含事实与语义，颜色 / 尺寸 / 布局由渲染器和宿主主题决定 | 2026-10-26 | 风格统一；模型无法破坏设计系统；同一份数据换主题即可换皮 | 允许模型给出样式提示（会逐步退化成“模型写 CSS”） |
| D3 | **自定协议，不直接采用 genui / A2UI**；字段形状对齐 A2UI，并写明映射表 | 2026-10-26 | Flutter 的 genui 包自称“highly experimental”且已宣布重写；新的 Flutter 渲染器尚未正式发布；A2UI 本身仍是早期预览（v1.0 为候选版）、没有 Rust 实现；其双向数据绑定与会话内 surface 状态不适合“消息持久化 + 离线同步”。对齐形状可以让将来的适配器只做机械映射 | 现在就依赖 genui / A2UI（跟随 0.x 的破坏性升级、依赖面大、默认 Material 组件）；完全不考虑 A2UI（将来迁移成本高） |
| D4 | **独立仓库、独立发布**，库不知道任何宿主业务 | 2026-10-26 | 强制边界：宿主概念无法“顺手”混进库；库可以被其他应用复用；版本与发布节奏独立 | 放在首个宿主的 monorepo 里作为子包（最省事，但耦合几乎必然发生） |
| D5 | **v1 流式**：Markdown 增量；组件块整块到达（`block.start` 占位、`block.data` 填满）；不做组件字段级增量 | 2026-10-26 | 满足“不等整条消息生成完”的核心要求，同时把复杂度控制在可验证范围；工具结果天然是整块到达的 | 字段级增量（需要部分 JSON 解析与逐字段 Schema 校验，留到 Phase 3）；不做流式（体验不达标） |
| D6 | **稳定块 ID + 按 ID 补丁 + `seq` 幂等 + `Last-Event-ID` 续传 + 快照回退；持久化版本优先** | 2026-10-26 | 移动网络下断线是常态；`seq` 让重复与跳号可判定；快照让服务端可以不长期保存事件；持久化版本优先让离线 / 多设备最终一致 | 尽力而为、断线重新生成（浪费模型调用且结果可能不同）；按到达时间合并（不可判定） |
| D7 | **传输用 SSE，每条消息一条流** | 2026-10-26 | 单向推送足够；普通 HTTP，鉴权与代理照常工作；自带续传约定；续传状态只需一个整数 | WebSocket（双向能力用不上、代理与重连更复杂）；按会话合并成一条流（续传状态更复杂，留待评估） |
| D8 | **v1 无 UI Agent，客户端注册表做确定性映射**；View 协议只保留字段名 | 2026-10-26 | 普通展示不额外调用模型：低延迟、低成本、可测试；渲染器不依赖模型也能工作 | 每条消息都经过 UI Agent（延迟与成本翻倍、结果不确定） |
| D9 | **v1 最小动作集**：`choice.select`、`confirmation.respond`、`form.submit`；服务端 Action Registry 做参数校验与宿主权限检查；破坏性操作只能经破坏性确认块；UI 动作 ≠ 工具授权 | 2026-10-26 | 覆盖澄清、确认、补充信息三种最常见交互；动作只能引用服务端持久化的声明，客户端与模型都无法凭空获得执行权限 | 完整交互体系（点击下钻、筛选等，留到 Phase 3）；客户端直接调用业务接口（绕过统一校验） |
| D10 | **服务端（宿主）把业务结果映射成块**；数字来自工具 / 业务查询，不由模型编造；纯文本 Agent 只降级为 Markdown，适配器不推断事实 | 2026-10-26 | 数据忠实；模型被注入也只能触发合法、已校验的块 | 让模型直接输出块 JSON（校验面大，数字可能被编造）；用正则从文本抽取组件（不可靠，且会“猜”出错误事实） |
| D11 | **语言无关规范 + JSON Schema 为准**，Rust 与 Dart 各自手写实现，用共用的一致性夹具保持一致 | 2026-10-26 | 规范可被第三种语言实现；夹具比代码生成更容易审阅 | 以 Rust 类型为唯一来源生成 Schema 与 Dart 代码（生成链复杂、Dart 侧可读性差） |
| D12 | **Flutter 分两层**：`chatweave_core`（纯 Dart）与 `chatweave_flutter`（界面） | 2026-10-26 | 协议逻辑可以在没有 Flutter 的环境里测试与复用；界面层可以被宿主替换 | 单包（宿主无法只用协议核心） |
| D13 | **存储、传输、权限、主题全部由宿主注入** | 2026-10-26 | 宿主已有离线数据库、HTTP 客户端、离线队列、鉴权与设计系统，库不重复造、不强加 | 库自带数据库与 HTTP 客户端（依赖冲突、与宿主离线策略打架） |
| D14 | **Markdown 用 `flutter_markdown_plus` 的受限子集**；不加载图片、不渲染 HTML | 2026-10-26 | `flutter_markdown` 已停更，`flutter_markdown_plus` 是官方指定继任者，依赖极少、样式可完全接管 | `gpt_markdown`（对 LLM 输出更友好，但依赖多、要求更高的 Flutter 版本，留作备选） |
| D15 | **自研聊天列表**（`CustomScrollView` + `SliverList`），`flutter_chat_ui` 作为备选 | 2026-10-26 | 流式占位、滚动锚定、golden 可控性需要完全掌控；依赖更少 | 直接采用 `flutter_chat_ui`（成熟但带入额外依赖，消息模型需要映射） |
| D16 | **主题接口支持深色**，但不要求宿主实现深色 | 2026-10-26 | 库要通用；有的宿主 v1 只做浅色 | 只支持浅色（将来再改接口成本高） |
| D17 | **许可证待仓库创建时添加**，预计 MIT（与首个宿主一致） | 2026-10-26 | 宽松许可便于复用 | — |
| D18 | **交互块不乐观显示结果**：点按后只显示“提交中”（离线时“已排队”），收到服务端补丁或同步版本后才显示结果；“提交中 / 已排队”是客户端本地状态，不进协议。取代架构草稿中“乐观显示已选择”的写法 | 2026-10-26 | 结果可能被拒绝、可能被别人抢先回答；先画“已选择”再回退会让用户以为已经生效。只显示服务端记录的结果，所有设备看到的永远一致 | 乐观显示已选择，失败再回退（多人场景下会短暂显示错误结果，回退体验差） |
| D19 | **交互块先答者胜**：`state` 增加 `resolvedBy`（不透明成员 ID）、`resolvedAt`（`resolved` 时必填）、`superseded` 状态与 `supersededBy`；去掉含义模糊的 `submitted`。块不再 `open` 时，拒绝结果（`already_resolved` / `expired` / `superseded`）**必须**带当前状态的补丁，客户端显示服务端的真实结果 | 2026-10-26 | 共享会话里同一张卡可能被多人同时看到；“检查 open → 写入”原子化后只有一个答案生效，其余客户端靠返回的补丁立刻对齐，无需再查一次 | 后写覆盖先写（结果不可预期）；拒绝时只给错误码（客户端还得另取状态才能显示） |
| D20 | **确认 D7：每条消息一条 SSE 流**，不按会话合并（原待定问题 1 关闭） | 2026-10-26 | 续传状态只是一个整数；v1 场景同一时刻通常只生成一条消息 | 会话级流（续传需要会话游标，复杂度高，等真实需求出现再评估） |
| D21 | **事件日志默认保留到 `message.end` 后 10 分钟**，宿主可配置；存放位置由宿主决定（原待定问题 2 关闭） | 2026-10-26 | 覆盖常见断线、切后台、弱网重连；更久之后走快照或同步即可，日志不必长期保存内容 | 长期保留（存储与隐私成本）；不保留（每次断线都只能快照） |
| D22 | **澄清问题的自由文本回答作为普通用户消息发送**，不走动作通道；宿主把它关联到仍为 `open` 的块并在服务端写成 `resolved`（`state.freeText`）。`choice.select` 的 payload 只含 `selected`（原待定问题 6 关闭） | 2026-10-26 | 用户打字回答本来就是一条消息，应该出现在对话里、能被搜索和引用；动作通道只承载“从声明的选项里选”，校验面更小 | 动作里带 `freeText`（文字回答不出现在对话流里，且有两条提交路径要对账）；两者都允许（同一意图两种形态，宿主要处理重复） |
| D23 | **客户端状态单一写入口**：`BlockStore.apply(event)` 是唯一的写路径；同步生效、一次写最多一次通知、无变化不通知且返回同一对象、结构共享 | 2026-10-26 | 所有状态变化可记录、可回放、可测；Flutter 侧可以按引用跳过重建 | 各处直接改模型（难以测试与调试，重复通知） |
| D24 | **续传触发与上限**：除断线 / 心跳超时 / 跳号外，打开会话、切回会话、网络恢复、回到前台时都检查未完成消息；同一消息只有一个续传在进行；连续追赶失败超过上限就改取持久化版本 | 2026-10-26 | 移动端后台常被静默断开，主动检查恢复更快；单飞避免重复连接；上限保证最终收敛到权威版本 | 只靠心跳超时（恢复慢）；无限重试（可能一直追不上） |
| D25 | **乐观用户消息按 `clientMessageId` 对账**，原地替换、行身份不变；重试复用同一 ID；绝不按文本、发送人、时间猜匹配 | 2026-10-26 | 猜匹配在重复文本、时钟偏差下必然出错；显式 ID 简单可靠 | 按内容和时间近似匹配（会错配或重复） |
| D26 | **按块错误隔离与注册规则**：每个块单独错误边界，失败降级为自身 `fallbackText` 并且每块只上报一次；同一类型可按谓词注册多个构建器，按顺序第一个命中胜出；内置类型只能显式 `override`；组件可声明依赖的宿主能力 | 2026-10-26 | 一个宿主组件的缺陷不应让整条消息或整个列表崩溃；显式覆盖避免无意中替换默认组件 | 整条消息级别的错误处理（一个块坏了整条消息退化） |
| D27 | **没有动作通道时交互块只读**：照常显示内容与结果，控件禁用；禁止把选项文字作为消息发出这种隐式回退 | 2026-10-26 | 隐式回退会绕过服务端校验、结果也无法对账；只读能保持信息完整 | 退化成发送文本消息 |
| D28 | **幂等键生命周期**：每次决定生成一次；网络错误 / 超时 / 离线重发复用同一 ID；只有明确拒绝后重新决定才换 ID；交互状态与幂等键放在 `chatweave_core`，不放在组件 State | 2026-10-26 | 超时不代表没执行；组件回收重建不能导致重复提交 | 每次点击都新 ID（超时后重试可能重复执行） |
| D29 | **动作错误分类扩展与文案原则**：新增 `superseded`、`rate_limited`、`unavailable`；区分 `forbidden`（这个人不能做）与 `conflict`（业务规则不允许）；`unavailable` 与客户端超时不显示为“失败” | 2026-10-26 | 结果未知时说“失败”会误导用户重复操作 | 只有一个通用失败码 |
| D30 | **只读调试面板**：`inspect()` 只读快照 + 最近 N 个事件的环形缓冲；`ChatWeaveDebugOverlay` 可选、由宿主决定启用方式、不进生产包；导出默认去掉正文与数据 | 2026-10-26 | 续传、补丁、降级问题靠日志很难复现；只读保证调试不改变行为；默认脱敏便于贴进公开问题报告 | 无调试工具；可写的调试面板（会改变被观察的行为） |
| D31 | **宿主实现一致性套件** + `MemoryTransport` / `ScriptedTransport`：宿主的存储与传输实现在自己仓库里跑库提供的契约测试；可选项跳过需写明原因，一条都没跑算失败 | 2026-10-26 | 夹具保证 Rust / Dart 一致，套件保证宿主实现符合接口约定；内存与脚本化传输让示例和组件测试离线可跑 | 只靠文档描述接口约定 |
| D32 | **滚动由纯函数 `ViewportController` 决定**（细化 D15）：锚点 = ID + 像素偏移；全库只有一处写滚动位置；“有新内容”与可见性回调从状态推导 | 2026-10-26 | 流式占位、组件变高、插入历史是聊天列表最难的部分，纯函数可以在纯 Dart 中单测 | 在组件里分散处理滚动（难测、易互相干扰） |
| D33 | **运行过程事件参照 AG-UI 1.0**：将来展示运行 / 工具进度时采用其事件名与字段，ChatWeave 信息放信封并维护扩展清单；Phase 3 的“确认后交回 Agent”用不透明 `toolCallId`，对齐其中断模式。v1 不实现 | 2026-10-26 | 内容对齐 A2UI、过程对齐 AG-UI，外部 Agent 和其他客户端更容易接入 | 自定一套运行事件（与生态不兼容） |
| D34 | **提供“在通用 IM 消息里承载 ChatWeave”的映射**（protocol.md 第 12 节），不改协议 | 2026-10-26 | 已有 IM 系统只需写一个渲染插件即可展示 ChatWeave 内容 | 为特定 IM 定制协议字段（耦合） |
| D35 | **时间统一用 RFC 3339**，协议内不混用 epoch 等其他编码 | 2026-10-26 | 一种编码，没有歧义 | 新旧字段各用各的格式 |
| D36 | **Markdown 规则补充**：单个换行即换行；宿主链接钩子（`isAllowedLink` / `onLinkTap`）；图片网址显示为链接；代码内不解释；`plainTextSummary()` 统一纯文本摘要 | 2026-10-26 | 贴合模型输出习惯；站内链接可路由；通知与预览的文本一致 | 严格 CommonMark（单换行被合并，列表式回答挤成一段） |
